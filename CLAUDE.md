# MTB DataLogger Analyzer — Project Context

## Overview
Python/Tkinter desktop application for analyzing MTB data logger CSV files.

- **Entry point:** `MTB_DataLog_Analyze.py`
- **Run via:** `source .venv/bin/activate && python MTB_DataLog_Analyze.py`
- **venv:** `.venv/` using Homebrew Python 3.14 (system Python incompatible with macOS Tk)
- **GitHub:** https://github.com/NightRider-2000/MTB_DataLogger_Analyzer

Distance needs the calibrated wheel speeds the calibration cascade builds, so `file_manager._load_from_paths` redraws the preview (`plot_signals`) once more after the cascade; header-less logs (no cascade) show Duration only. **The right panel has TWO stacked views toggled by file type** (`_build_plots_panel` in MTB_DataLog_Analyze.py builds both in one cell): the **preview view** (`_preview_view` — the time-series + histogram, for ride CSVs) and an **EventLog table view** (`_eventlog_view`). When a selected file's basename starts with `EventLog` (case-insensitive), `file_manager._on_file_select_settled` calls `_show_eventlog(path)` — reads the CSV as strings and renders it as a **wrapped, scrollable table** (`_build_eventlog_view` / `_populate_eventlog_table`) instead of loading it as a ride; ride CSVs call `_show_preview_view()` first to restore the plots. The table is a Canvas + Frame grid of wrapping Labels over a `TABLE_GRID` background (ttk.Treeview can't wrap — same word-wrap pattern as the Device Config editor); short columns are fixed-width (`_EVTLOG_COL_W`), the `message` column flexes with `weight=1` and its `wraplength` tracks the canvas width (`_eventlog_on_canvas_configure`) so all columns stay visible with no horizontal scroll. The **header row is frozen** — it's a separate Frame above the scrolled canvas (`_eventlog_header`), given the same per-column config as the body grid and stretched to the same width, so columns stay aligned and the header stays visible while scrolling. EventLog selection does NOT touch `self.df` (the loaded ride stays intact on the analysis tabs). The Select Data **left panel is a FIXED 350 px width** (`center.columnconfigure(0, weight=0, minsize=350)` in `_build_import_tab`) so it never changes when the right side switches between the plot preview and the EventLog table

imu.py            — ImuMixin: IMU tab (histograms + bike picture + axis diagram). No board picture — removed 2026-07 (SparkFun board no longer used); the axis diagram now takes the full width of that row and self-centers via `set_aspect("equal")`
gps.py            — GpsMixin: GPS tab (satellite route map + colored time-range bar + global time filter)
basemap.py        — Esri World Imagery + Terrarium DEM XYZ tile fetch/stitch (stdlib urllib + pillow); Web-Mercator helpers
frequency.py      — FrequencyMixin: Frequency tab, split into two side-by-side panes. **Left**: overlaid PSDs of up to 3 selectable signals (combos + color dots like the Time Series page; defaults Front/Rear_Wheel_Pos_mm + aVert_g), 0.05–60 Hz frame (`_FREQ_MAX_HZ` — both panes; real content lives below 60, half the Nyquist 120), per-signal >1 Hz peak annotation. **Right**: **PSD-vs-X map** (order analysis, `_compute_spec_panel`) — STFT (`scipy.signal.spectrogram`, nperseg 1024 ≈ 4.3 s → ~0.23 Hz bins; rows above `_FREQ_MAX_HZ` trimmed before binning so color contrast reflects only the displayed band) of a selected signal; each STFT column tagged with the mean of a selectable x-signal over its window (default synthetic **"Avg Wheel Speed (mph)"** = row-mean of both wheels; second synthetic option **"Time (s)"** = elapsed seconds → a classic spectrogram, binned much finer — up to the STFT column count — so time structure isn't averaged away); columns binned by x (40 bins for value axes), linear-power averaged, shown as a `pcolormesh` dB map (plasma, robust 1–99 pct color range, colorbar in a FIXED gridspec cax — never `fig.colorbar()` per redraw, it stacks axes). Speed-proportional excitation (wheel imbalance, tire knobs) → diagonal ridge; speed-independent (steady-cadence pedal bob) → horizontal. X-alignment onto the resampled index is positional (`searchsorted`) — `reindex(method="nearest")` raises on duplicate timestamps. Compute is opt-in via the button (see Performance section); changing any selector recomputes immediately once data is loaded (~0.2 s on an 81-min ride). Both plots carry a `NavigationToolbar2Tk` (rect-zoom/pan/home, `_freq_add_toolbar`) — the Select Data "no toolbar" rule applies only to that tab's quick-glance preview. Panes are a strict 50/50 split (`grid uniform`)
time_series.py    — TimeSeriesMixin: **6** stacked time-series plots (`_N_PLOTS`), **4** signals each (`_N_SIGS`), sharing an x-nav (zoom/pan/reset). The plot list lives in a **vertically-scrollable canvas** (nav bar fixed on top); each section is a fixed `_SECTION_H` px (pack_propagate off) so the content overflows and scrolls, mouse-wheel bound only while the pointer is over the area. Every plot carries its own HH:MM:SS.mmm x tick labels (no single shared "bottom" axis). Per-slot colors `_TS_COLORS` = **red, blue, yellow, green** (slots 0-3). **Each signal's y-axis (left/primary or right/secondary) is user-selectable** via a **framed arrow BUTTON** above the plot (`_ts_axis_btns`, a raised-relief `tk.Label` in the signal's color): **◀** = left, **▶** = right; **click toggles** it (`_ts_toggle_axis` flips `_ts_axis_side[plot][slot]` "L"/"R", updates the glyph, redraws). **Default** is slots 0-2 → left and slot 3 (green) → right (unchanged from before). The right y-axis (`_ts_axes2`, an `ax.twinx()` per plot) auto-scales independently so a very-different-range signal can share the plot (`_ts_autoscale_y` runs on both axes); `_ts_style_secondary` hides it when no slot is on the right, colors it to that signal when exactly one is, and goes neutral DARK when several are. **Marginal histogram** (`_ts_hist_axes`, `_ts_draw_hist`) to the LEFT of each plot: the distribution of the **LEFT-axis signals only** (right-axis signals are excluded — different scale; the histogram reads `ax.get_lines()`, and only left signals are plotted to `ax`), binned along the **shared value (y) axis** so the bins line up with the plot's y-axis, drawn horizontally (counts grow leftward, x inverted). It shows **only the data in the current x-window** and is recomputed on every draw and every pan/zoom (`_ts_set_xlim`). Each signal also gets its **median** over the visible window: a dashed marker line at the median value + a `med <val>` text label **color-coded to the signal**, stacked at the top so they stay legible when medians are close. The value tick labels live on the histogram (far left); the time series hides its own. `gridspec` width ratio 1:6. **Y-axis auto-fits the data visible in the current x-window** on every draw and every nav action (`_ts_autoscale_y`) — floats to the visible min/max (5% pad) even when that min is > 0, never anchored at zero. Uses `line.get_xdata(orig=False)` so the x-data is in the axis' float date-number units (plain `get_xdata()` returns datetime objects that wouldn't match `get_xlim()`); no visible data in the window → leaves y unchanged. **Filtered-region highlighting:** unlike every other analysis tab (which read the filtered `cal_result_df`), Time Series plots the **FULL unfiltered frame** via `_ts_source()` → `self._cal_full`, so rows the stopped/walking auto-filters exclude stay VISIBLE. Those excluded time regions are shaded **light transparent red** (`TS_FILTER_SPAN_COLOR`, alpha `_TS_FILTER_SPAN_ALPHA`) by `_ts_draw_filter_spans(ax)` — the union of whichever of the stopped/walking checkboxes are currently ON, one `ax.axvspan` per contiguous mask run in `mdates.date2num` units (so the spans line up with the lines and survive pan/zoom without a re-plot; they're `Polygon` patches, zorder 0, so they don't affect `_ts_autoscale_y` which reads `ax.get_lines()`). The interval list is computed once per redraw by `_ts_filter_intervals()` and cached on `self._ts_filt_intervals`, so pan/zoom reuse it. **The marginal histograms EXCLUDE the filtered samples**: `_ts_draw_hist` drops any x inside `_ts_filt_intervals` (flat sorted edges + a `np.searchsorted(...,'right') % 2` parity test), so the distribution AND the median reflect only the KEPT (unfiltered) data even though the full trace is drawn through the red-shaded regions. Toggling a filter checkbox redraws both the shading and the histograms via `_refresh_all_analysis_tabs → _refresh_ts_signals`. ⚠ Because it uses `_cal_full`, Time Series also ignores the GPS time-window filter — it always shows the whole ride (its own zoom/pan nav is the way to focus)
susp_speed.py     — SuspSpeedMixin: works in **SHAFT speed** (`Fork_/Shock_Shaft_Spd_mmps` — savgol derivative of the raw sensor/shaft position, the quantity damper circuits actually see; wheel-vertical speeds still exist for other tabs). Left column = comp/rebound shaft-speed histograms (front/rear, x-linked, shared 98th-pct range, legend shows n/mean/max). Right column = **position-vs-shaft-speed 2D histograms** (fork top, shock bottom): `hist2d` of `Fork_/Shock_Pos_Perc` (x, linked + shared range) vs shaft speed (y), **adaptive bin count** `≈ sqrt(N/_MAP_MIN_PER_BIN)` clipped [20,100] so a typical bin holds ≥50 samples (smooth color field, not speckle), `LogNorm` + `cmin=1` (empty bins → BG), robust percentile ranges, fixed gridspec colorbar axes (never `fig.colorbar()` per redraw), Comp below / Rebound above the y=0 dashed line. **LS↔HS damping transition band** (`SUSP_LSHS_BAND_MMPS` = 150–300 mm/s shaft speed, constants.py) shaded green on all four plots (both signs on the maps) — a BAND, not a line, because the true crossover is damper/adjuster dependent (blow-off initiation ~150 mm/s ≈ 6 in/s per published tuning references); shaft-speed basis means no motion-ratio conversion. The old front-vs-rear speed scatter (wheelbase time-alignment) was REMOVED (2026-07-13)
free_plot.py      — FreePlotMixin
sag.py            — SagMixin
bike_params.py    — BikeParamsMixin: constants organized into **titled card-tables** (`_card` = bordered frame w/ DARK header bar; `_fr_row` = Front/Rear 2-column, `_kv_row` = single value). **Suspension** (spring rate / preload / fork-shock travel / **Vertical Wheel Travel**, front+rear), **Bike Geometry** (head-tube angle, wheel base, chainstay length, front center length [derived = wheelbase − chainstay via `_upd_front_center`], BB height, IMU pitch offset), **Drivetrain & Wheels** (wheel circumference + triggers/rev front/rear, crank triggers/rev, chain-ring teeth), plus the **Rear Suspension Motion Ratio** (Treeview + Load/Save + **Leverage Ratio plot** — dWheel/dShock vs Rear Suspension Vertical Travel) and **Cassette Gears** (12-row Treeview). All cards sit in a visible box (the `_card` outline is a 1-px `TABLE_GRID` outer frame — reliable on macOS where a Frame's `highlightthickness` border can fail to paint). Front **Vertical Wheel Travel** = fork travel·sin(HTA) auto-computes from the fork-travel + head-angle fields (`_upd_fst`); **rear Vertical Wheel Travel** derives from the MR table at max shock stroke (`_recompute_rear_wheel_travel`, re-run on shock-travel / MR-table edits); those + IMU offset trigger `_apply_all_calibrations`, fork/shock travel triggers `_update_sag_plots`. All `*_var`/`_*_entry` attribute names preserved (calibration.py depends on them)
device.py         — DeviceMixin: Device tab (USB serial → Teensy MTB protocol)
MTB_DataLog_Analyze.py — MountainBikeApp + __main__

## Dependencies
- `pyserial` — required for the Device tab (USB serial to Teensy). Install in venv: `pip install pyserial`
- `scipy` — Savitzky-Golay suspension velocity (`scipy.signal.savgol_filter`) and quaternion→Euler attitude (`scipy.spatial.transform.Rotation`). Install in venv: `pip install scipy`
- `matplotlib`, `pandas`, `numpy`, `pillow` — standard data/plot stack (`pillow` also stitches satellite tiles for the GPS tab)
- GPS tab satellite imagery + topo contours need internet for the first fetch (Esri World Imagery + Terrarium DEM tiles, then disk-cached); no extra pip package — tiles come via stdlib `urllib`. Offline → plain lon/lat map with no contours.

## Architecture
- Class: `MountainBikeApp(FileManagerMixin, PlotsMixin, CalibrationMixin, tk.Tk)`

## Plotting Standards

### Figure & Canvas
- Create figures with `w.make_figure(figsize=..., dpi=100)` — sets `fig.patch.set_facecolor(BG)` automatically
- Create canvases with `w.make_canvas(fig, parent)` — sets widget `width=1, height=1` to let grid control size
- After `add_subplot`: always set `ax.set_facecolor(BG)`
- When redrawing: `ax.clear()` then `ax.set_facecolor(BG)` before any plot calls
- Always call `w.style_ax(ax)` as the last step before `canvas.draw()` — applies tick/spine colors and grid
- Layout: always `tight_layout()` wrapped in `warnings.catch_warnings()` + `warnings.simplefilter("ignore")`. Use explicit `fig.subplots_adjust(...)` only when stacked figures must share a locked x-axis (e.g., Time Series tab)

### Colors
- All plot text (titles, axis labels, tick labels, legend text, annotation text): `DARK`
- Figure and axes backgrounds: `BG`
- Grid lines (via `style_ax`): `GRID`, `linewidth=0.7`, `linestyle="-"`, `set_axisbelow(True)`
- Multi-signal coloring: `HIST_COLORS[i % len(HIST_COLORS)]`
- **All plot-specific semantic colors must live in `constants.py`** — no inline hex strings or module-level color constants in individual plot files

### Font Sizes
**Global scale + offset:** all UI/plot text is sized as `round(base × FONT_SCALE) + FONT_DELTA` (`constants.py`: `FONT_SCALE = 1.7`, `FONT_DELTA = -2`). The `-2` is a global point trim applied on top of the scale. It is applied three ways: Tk named fonts in `theme._scale_named_fonts` (`round(size*FONT_SCALE)+FONT_DELTA`), matplotlib `rcParams["font.size"]` at the top of `MTB_DataLog_Analyze.py` (`*FONT_SCALE+FONT_DELTA`; relative sizes cascade), and the explicit `fontsize=` / `font=(…)` literals are baked at the final value in the source. The table below lists the **base** (pre-scale) design sizes — the literals in code are `round(base×FONT_SCALE)+FONT_DELTA` (e.g. base 9 → `round(15.3)−2 = fontsize=13`). To retune everything: change `FONT_SCALE`/`FONT_DELTA`, then re-bake every literal (`fontsize=` and Tk `font=(…)` tuples) to the new value.

| Element | Standard panel (base) | Compact subplot (base) |
|---|---|---|
| Title | `9` | `8` |
| Axis label | `8` | `7` |
| Legend | `7`–`8` | `7` |
| Annotation/stats text | `7` | `7` |
| Row/figure label | `10`, `fontweight="bold"` | — |

### Legend
Always use: `fontsize=7` (dense/small) or `fontsize=8` (full-size panels), `facecolor=BG, edgecolor=DARK, labelcolor=DARK`

### Histograms
- **RULE — histograms are drawn as LINES, not bars.** Always use `w.plot_hist_line(ax, data, bins, color, label=…)` (widgets.py), never `ax.hist()`. It bins with `np.histogram` and plots bin **centers vs counts** as a straight-segment frequency polygon (closed to zero at the outer edges) — a line, no curve smoothing. It returns `(counts, bin_edges)` (same leading tuple as `ax.hist()`) for callers that need them (e.g. `sag.py`'s percentile-zoom y-scaling). `bins` may be an int or a shared edge array (overlaid signals — `susp_speed.py` compression/rebound — pass the same `np.linspace(…, HIST_BINS+1)` edges so they line up).
- **RULE — 2+ histograms on the same Axes MUST share bins.** Whenever more than one histogram is drawn on one plot (Select Data preview with multiple signals, Free Histogram overlay, each IMU group, Susp Speed compression/rebound), compute one common edge array with `w.shared_bin_edges(list_of_datasets, bins)` and pass it to every `plot_hist_line` call on that Axes — never let each signal bin over its own range (independent bins misalign the lines and misrepresent where the distributions overlap). Single-histogram Axes may pass an int bin count directly. `susp_speed.py` shares via an explicit `np.linspace(0, bin_max, HIST_BINS+1)` (both series are ≥0, so the range is pinned to start at 0).
- Bins: **`HIST_BINS` (120)** standard; **`HIST_BINS_COMPACT` (90)** compact multi-signal panels (IMU) — both in `constants.py`, tune there. Fewer than a bar chart on purpose: a line at 200 bins reads jaggy.
- Lines are opaque (no alpha), `linewidth=1.5`; distinguish overlaid signals by color (`HIST_COLORS[i]`), not transparency. (2D density stays `hist2d`; that's not a 1-D histogram.)
- Vertical lines: mean `linestyle="--" linewidth=1.5`; median `linestyle=":" linewidth=1.5`; min/max `linestyle="--" linewidth=1.5`; std span `axvspan alpha=0.12`
- Stats annotation (mean/median/std/min/max): required on all histograms **except** IMU group histograms
  - Position: `(0.97, 0.97)`, `va="top"`, `ha="right"`, `transform=ax.transAxes`
  - Style: `fontsize=7`, `color=DARK`, `bbox=dict(boxstyle="round,pad=0.4", facecolor=BG, edgecolor=GRID, alpha=0.9)`
  - Format: `f"{col}\n  mean={mean:.4g}\n  med ={med:.4g}\n  std ={std:.4g}\n  min ={mn:.4g}\n  max ={mx:.4g}"`

### Time Series Plots
- **Always plot via `w.plot_time_series_smart(ax, series, color=..., label=...)`** (widgets.py) — never a bare `.plot()`/`ax.plot()` call for a raw or calibrated time-domain signal. It calls `insert_gap_nans` internally, then: sparse signals (>50% NaN after gap insertion — GPS fixes, trigger-driven wheel speed, etc.) get dots (`marker="."`, `markersize=3`, `linestyle="none"`); dense signals get a normal connected line. **A connected line across mostly-missing data is either invisible (no two valid samples are ever adjacent) or misleadingly continuous** — this was a real bug (2026-07): the Select Data tab's raw preview (`plots.py plot_signals`) used a bare `DataFrame.plot()` with no sparse handling, so GPS (~99% NaN — only present once a fix is acquired) rendered as nothing and trigger-driven wheel speed (~90% NaN) rendered as disconnected, easy-to-miss fragments instead of a visible dot cloud. `time_series.py` already had the correct per-column logic inline; it's now the shared implementation both tabs call.
- **RULE — time-axis tick labels are always `HH:MM:SS.mmm`, never day/month/year:** call `w.format_time_axis(ax)` (widgets.py) on every axis whose x-data is a real datetime axis (a pandas `DatetimeIndex` plotted directly — Select Data preview, Time Series tab, Signal Calibration raw/calibrated panels). Matplotlib's default date locator/formatter otherwise prints a date once the axis is zoomed out far enough, which this project never wants. Call it right after `w.style_ax(ax)`. Do NOT call it on non-time axes (histograms, free-scatter plots of two arbitrary signals, PSD/frequency plots) — it would print garbage labels there. The GPS tab's ride-timeline bar is a special case (an elapsed-seconds axis, not a real datetime axis) — it has its own `_gps_time_formatter` in `gps.py` that follows the same HH:MM:SS.mmm convention by construction; don't route it through `w.format_time_axis`.

### Scatter Plots
- Points: `s=8`, `alpha=0.5`, `linewidths=0`
- Trend line: `TREND_COLOR` (from `constants.py`), `linewidth=1.8`, `linestyle="--"`
- Bin mean line: `BIN_MEAN_COLOR` (from `constants.py`), `linewidth=2.0`, `marker="o"`, `markersize=5`
- ±1σ fill: `alpha=0.20`
- Use 20 bins across the x range for binned statistics

### 2D Histograms & Colormapped Scatter
- `hist2d`: `bins=100`, `cmap="hot"`
- Scatter with color axis: `cmap="plasma"`, `s=8`, `alpha=0.5`, `linewidths=0`
- Colorbars: `set_label(..., color=DARK)`; tick params `color=DARK`; all tick labels `.set_color(DARK)`

### PSD / Frequency Plots
- Lines: `linewidth=1.2`
- Peak frequency annotations: `fontsize=7`, `va="bottom"`
- **X-axis fixed at 0.05–120 Hz** (`frequency.py _compute_frequency_plot`). `Front_Wheel_Pos_mm`/`Rear_Wheel_Pos_mm`/`aVert_g` are all logged at 240 Hz (`config.h IMU_ODR_HZ` / analog decimation — see Teensy_MTB_DAQ `CLAUDE.md`), so 120 Hz IS the Nyquist limit — nothing above it can be real content. (History: briefly set to 200 Hz on 2026-07-05 with a Nyquist marker line, then capped to 120 Hz since that equals Nyquist and made the separate marker redundant.)

## Widget & Text Standards

### Buttons
- Always use `w.make_btn(parent, text, command, style="Dark.TButton")` — renders a `ttk.Button`. The optional `style=` arg selects a registered variant (default `Dark.TButton`)
- **Variants** (both defined in `theme.py` → `setup_theme`):
  - `Dark.TButton` — standard; font = scaled `TkDefaultFont`, padding `[8, 4]`
  - `Small.TButton` — compact; font ≈ `0.7×` the scaled default, padding `[4, 2]`. Used by the **Device tab** (every button there goes through the `device._dev_btn` helper) so the SD/host button rows fit on screen
- Never construct a `ttk.Button` directly or set style/colors inline; new button variants go in `theme.py`
- **Visual spec** (defined in `theme.py` → `setup_theme`):
  - Normal: `background=DARK` (`#1b3a6b`), `foreground=BTN_FG` (`#ffffff`)
  - Hover/active: background `#2a5298`
  - Disabled: background `FIELD` (`#a8b2bc`), foreground unchanged
  - Padding: `[8, 4]` (horizontal, vertical); `borderwidth=0`, `relief="flat"`, `focusthickness=0`
- **Enabling / disabling** — call `.configure(state=tk.NORMAL)` or `.configure(state=tk.DISABLED)` on the saved reference; the `FIELD` background is applied automatically by the ttk style map
- **Toggle-text buttons** (e.g. Connect/Disconnect) — save the reference, call `.configure(text="...")` to relabel in-place; do not destroy and recreate
- Pack with `padx=2` inside a toolbar row; `padx=5` in top-of-tab button bars; `padx=6` for connection controls

### Entry Fields
- Always use `w.make_entry(parent, width=N)` — applies `bg=FIELD`, `fg=DARK`, flat relief, dark border highlight

### Listboxes
- Always use `w.make_listbox(parent, selectmode=...)` — standardizes colors, selection highlight, and border
- The **Select Data** file browser is a `ttk.Treeview` (not a Listbox) — see Tab Notes below

### Tables (ttk.Treeview) — RULE: gridlines on every cell
- **Every table shows solid grey gridlines around every cell** — color `TABLE_GRID` (`#808080`, `constants.py`), 1 px, opaque. No table may render without them.
- **Table font**: all table text (Treeview body + headings + the config-grid cells) uses the named font `TableFont` = scaled default − 2 pt, created in `theme.setup_theme` (kept alive by a module-level ref — `Font.__del__` deletes named fonts on GC). Treeview `rowheight` is derived from it (`linespace + 8`). New tables/custom grids must use `font="TableFont"`, never the default font.
- Implementation (requires Tk 9 — the Homebrew tcl-tk the venv links against):
  - *Horizontal*: `theme._setup_table_gridlines` appends a 1-px `TABLE_GRID` image element (`Gridline.hline`) to the bottom of the shared `Row` layout — applies to all treeviews automatically, and tag/selection backgrounds keep working (the line draws on top).

Name", `Raw_Sig_Min` → "Raw Min", `Value_at_Max` → "Val Max", etc.), with column widths measured against `TableFont` (`font.measure`) to confirm each actually fits. ## Auto-Filters — Stopped Times + Walking (calibration.py)
Two independent default-on filters that exclude non-riding data, both computed at the end of `_apply_all_calibrations` on `_cal_full`, cached as `_stopped_mask`/`_walking_mask`, exposed as plottable `Stopped`/`Walking` 0/1 columns, and composed (with the GPS time window) in `_recompute_filtered_view`. Each has a checkbox on the Select Data tab.

### Auto-Filter Stopped Times
- **Rule:** the bike is *stopped* when the **wheels aren't turning AND the rider isn't pedaling**, sustained ≥ `STOPPED_MIN_S`. Detection uses **only** wheel speed + crank — **GPS is not used** (too noisy), and **suspension and IMU are deliberately not used** (a design decision — a rider resting on a stationary bike is still "stopped").
- **`_compute_stopped_mask(df)`** returns a positional bool array (True = stopped): `wheel_still = (Front_Horz_Wheel_Spd_mph isna | < STOPPED_WHEEL_MPH) & (Rear_… )` AND-ed over whichever wheel channels have real data; `pedaling = Crank_Spd_RPM.notna() & (> STOPPED_CRANK_RPM)`; `stopped_raw = wheel_still & ~pedaling`. Wheel speed is already NaN whenever there's been no trigger in ~0.5 s (see `_derive_speed` ffill limit), so a missing/near-zero reading *is* the "not turning" signal; crank overrides because a slow/techy section has sparse wheel triggers but real motion (coasting has no crank signal, which is why crank can only ever *add* "moving" evidence, never declare stopped). **All-False (filter nothing) when there's no usable wheel data** — a wheel-sensor-dead ride isn't wiped out.
- **Asymmetric hysteresis** (both thresholds → samples via `w.sample_period_s`, never hardcoded):
  - *Exit-stopped* — `_bridge_short_gaps(stopped_raw, STOPPED_RESUME_S)`: a stop only ends after **sustained movement ≥ `STOPPED_RESUME_S`**. Any movement run shorter than that which is flanked by stopped on both sides is re-marked stopped (a brief shuffle / stray trigger doesn't un-stop the bike). A qualifying movement run is left intact, so it reads as **moving from its first sample** ("forward-looking permissive" — its leading seconds aren't counted as stopped). Movement runs touching a data edge are left as movement.
  - *Enter-stopped* — `_min_run_mask(…, STOPPED_MIN_S)`: then drops any remaining stopped run shorter than `STOPPED_MIN_S` so the ride isn't fragmented by brief trigger gaps.
  - Verified on synthetic patterns: 3 s move between stops → merged; 5–6 s move → kept as moving; 2 s still during riding → dropped; leading 5 s move → stop starts *after* it.
- Thresholds live in `constants.py`: `STOPPED_WHEEL_MPH=0.5`, `STOPPED_CRANK_RPM=5.0`, `STOPPED_MIN_S=3.0`, `STOPPED_RESUME_S=5.0`.
- **Plottable `Stopped` signal** (0.0/1.0) is added to `_cal_full` for verification — view it on Time Series / Free Plot to eyeball detection against wheel speed. (With the filter *on*, stopped rows are dropped so `Stopped` reads 0 across the view; turn the filter *off* to see the 1-regions it would drop.) It's a ride-state signal, not a per-value validity flag, so it's exempt from the "no companion boolean" rule.
- **Validation (2026-07-11, ride 20260710_144915):** 20 stopped runs, 902 s / 19.9% of the 81-min ride (with resume hysteresis; was 23 runs / 17.8% before it, as brief mid-stop moves now merge adjacent stops). GPS cross-check (not used in detection): median `gps_spd_mph` 0.38 during stopped vs 4.10 while moving.

### Auto-Filter Walking
- **Rule:** the bike is being *walked* (not ridden) during a **long continuous stretch (≥ `WALK_MIN_S`) of very slow wheel movement with the rear suspension near topout (`Rear_Wheel_Pos_Perc` < `WALK_REAR_COMP_PERC`)** — slow, but no rider weight on the bike. The speed test is a **centered rolling average** (not the instantaneous value). GPS and IMU are unused.
- **`_compute_walking_mask(df)`** returns a positional bool array (True = walking): `wheel_spd = row-max of Front_/Rear_Horz_Wheel_Spd_mph` (skipna), averaged over a **centered `WALK_SPEED_WIN_S` window** (2 s each side; `rolling(win, center=True, min_periods=1).mean()`, nan-aware, `win` forced odd) → `slow = avg_spd < WALK_MAX_MPH` (a window with no reading at all → NaN avg → not slow, so a **fully-stopped span is excluded** — that's the Stopped filter's job). `uncompressed = Rear_Wheel_Pos_Perc < WALK_REAR_COMP_PERC` (per-sample; NaN → not walking). `walking_raw = slow & uncompressed`; then `_min_run_mask(…, WALK_MIN_S)` keeps only **continuous** runs ≥ `WALK_MIN_S` (no bridging/resume hysteresis — the spec is a strictly-continuous walk). All-False when `Rear_Wheel_Pos_Perc` or all wheel speeds are absent.
- Distinguisher vs Stopped: walking requires the wheels to be **turning slowly** (windowed avg < 5 mph, with readings present) and no rider sag; stopped requires the wheels **not turning at all**. The two masks don't overlap in practice.
- Thresholds in `constants.py`: `WALK_MAX_MPH=5.0`, `WALK_SPEED_WIN_S=4.0`, `WALK_REAR_COMP_PERC=12.0`, `WALK_MIN_S=8.0`.
- **Plottable `Walking` signal** (0.0/1.0) on `_cal_full`, same use as `Stopped`.

## GPS Tab (gps.py — GpsMixin)
- One matplotlib figure, gridspec `(2,2)` height `[1,11]` width `[40,1]`: a thin **time-range bar** spanning the top, the **route map** bottom-left, a **colorbar** bottom-right. Controls above: "Color by:" combobox, Apply Filter / Clear Filter buttons, a window-readout label.
- **Time bar**: the selected signal binned over the full ride (`scipy.stats.binned_statistic`, `_STRIP_BINS=1200`) drawn as a 1-row `imshow` strip; x-axis is seconds-from-start with a `FuncFormatter` showing `HH:MM:SS`. Two **draggable markers** (`axvline` with `ymin/ymax` beyond [0,1] and `clip_on=False` so they spill above/below the strip as grab handles) define the window — **green = start (earlier), red = finish (later)**. `_gps_color_markers` recolors by time value on every move, so green/red stay correct even when a marker is dragged past the other. Empty time bins render as `BG` via `cmap.set_bad`.
- **Map**: a **satellite basemap** (Esri World Imagery) with the active route plotted on top, colored by the chosen signal; colorbar range = the signal's min/max.
  - `basemap.py` fetches XYZ tiles via stdlib `urllib` (no geo deps), stitches them with pillow, and returns the image + its Web-Mercator extent. Tiles are disk-cached in `tempfile.gettempdir()/mtb_sat_tiles`. The route and grey preview are projected to **Web Mercator** (`basemap.lonlat_to_mercator`) so they align with the tiles; ticks are hidden, with an Esri attribution label.
  - **Fills the window width**: `_gps_ensure_basemap` expands the full-route bbox to the *map axes' width/height ratio* (`_gps_axes_aspect`, from `get_position` × figure size) so the satellite spans the whole panel undistorted, with the route centered; `set_aspect("equal", adjustable="datalim")` keeps it filling. A debounced `resize_event` handler (`_gps_on_resize` → `after(200, _update_gps_plots)`) re-frames on window resize.
  - The basemap is fetched for that **aspect-filled** bbox and cached on the mixin (`self._gps_basemap`/`_gps_merc_limits`, keyed by the rounded bbox), so it is not refetched on filter/recolor — only when the bbox or window aspect changes.
  - **Offline fallback**: if any tile fails to download, `fetch_satellite_basemap` returns `None` and the map falls back to a plain lon/lat scatter (`aspect 1/cos(lat)`, visible axes). `self._gps_use_merc` records which mode is active and `_gps_project` picks the matching coordinates.
- **Pan / zoom (slippy-map UX)**: left-drag the map to pan (`_gps_do_pan` uses the pixel→data scale captured at press so the grabbed point stays under the cursor), scroll-wheel to zoom around the cursor (`_gps_on_scroll`, 0.8/1.25 factor). Uniform transforms preserve the equal-aspect framing so `adjustable="datalim"` never fights the gesture. On gesture-end a debounced `_gps_schedule_nav → _gps_apply_nav` locks the user's limits into `self._gps_view` and re-runs `_update_gps_plots`, which **refetches satellite + DEM tiles for the visible extent** at a `_pick_zoom`-appropriate level — so imagery (and contours) re-sharpen as you zoom in, like Leaflet/Google Maps. "Reset View" (`_gps_reset_view`) clears `_gps_view` back to the auto route-fit; loading a new ride also resets it. While `_gps_view` is set, filter/recolor/marker-drag redraws keep that view instead of refitting.
- **Topo contour lines** (checkbox "Topo lines", default on): `basemap.fetch_elevation_grid` pulls Terrarium DEM tiles over the *same* tile grid as the satellite (so the extent matches exactly), decodes elevation (`R*256+G+B/256-32768`), and `_draw_topo_contours` overlays `ax.contour` lines (interval auto-chosen 10–100 m from the local relief, downsampled for speed, labeled). Cached alongside the basemap (`self._gps_elev`). Only drawn in Mercator/satellite mode; absent/flat terrain simply yields no lines.
- **Color signal**: any numeric `cal_result_df` column (combobox), plus a synthetic **"Time (s)"** option (`_TIME_COLOR_KEY`, listed first) that colors by elapsed seconds from ride start. Default is the first present of `Rear_/Front_Horz_Wheel_Spd_mph`, `gps_spd_mph`, `Crank_Spd_RPM`. Both the time bar and the map resolve the choice through the single helper `_gps_color_values(df, col)` — it returns `_gps_secs(df.index)` for the synthetic key, `df[col].ffill()` for a real column — so the two views never diverge. The same scale drives both.
- **Start/finish circles**: two large circles on the map (`_draw_endpoints`) — one **green** at the route point nearest the start marker, one **red** at the finish marker — updated live on drag via `set_offsets` (`_update_endpoints`, nearest-time lookup against `_gps_route_secs`; full route is not re-scattered). Lets you scrub the window endpoints and see their geographic location.
- **Drawing source**: the time bar + grey preview always use the **full** cached frame `self._cal_full` (so the whole ride stays selectable); the colored map uses the **active** `self.cal_result_df` (full or filtered).

## Global filters — Stopped + Walking + GPS time window (calibration.py `_recompute_filtered_view`)
- `_apply_all_calibrations` caches the full result as `self._cal_full`, computes `self._stopped_mask` + `self._walking_mask`, and resets `self._time_filter=None`. Every analysis tab reads `self.cal_result_df`, so filtering is just a **positional boolean slice** of the cached frame — no recompute, no per-tab changes.
- **`_recompute_filtered_view()` is the single point that rebuilds the view**, composing every active filter: `cal_result_df = _cal_full[ (~stopped if its box on) & (~walking if its box on) & (time window if `_time_filter` set) ]`, then `_refresh_all_analysis_tabs()`. Uses a numpy mask so duplicate multi-file timestamps can't cause index-alignment blow-ups.
- **GPS time window** (`gps._apply_time_filter(tmin,tmax)` / `_clear_time_filter`) just set/clear `self._time_filter` and delegate to `_recompute_filtered_view()`. **Both auto-filter checkboxes** (`_on_toggle_auto_filter`, import tab) do the same. All three stack automatically.
- Apply/Clear Filter buttons map the marker window → timestamps and call those. Reloading data or re-running calibrations clears the time filter and resets the markers (`_gps_reset_markers`); the stopped + walking masks are recomputed for the new ride.

## MTB Serial Protocol (device.py ↔ Teensy sd_transfer.cpp)
- ASCII command/response on USB CDC, with two exceptions: `MTB:GET` interleaves a raw binary block between `MTB:SIZE:<n>` and `MTB:CRC32:<hex>`, and `MTB:PUT` receives one after `MTB:READY`
- Commands: `MTB:STATUS`, `MTB:LIST`, `MTB:GET:<name>`, `MTB:DEL:<name>`, `MTB:PUT:<name>:<size>`. All replies terminate with `MTB:END`
- Upload (`_cmd_put`): host sends the command line, waits for `MTB:READY`, streams `<size>` raw bytes, then reads `MTB:CRC32:<hex>` + `MTB:OK` + `MTB:END`. The device stages bytes in `UPLOAD.TMP` and atomically renames over the target, so a failed upload never corrupts the existing file; host verifies the returned CRC against its own `zlib.crc32`. 64 KB size cap (config-scale files)
- Download integrity: the Teensy holds `_transferActive=true` for the whole duration including the trailing `MTB:CRC32` and `MTB:END` lines so the dashboard thread can't splice text into the binary stream or the CRC line. CRC32 verified on host via `zlib.crc32` (matches Teensy `crc32_update`); mismatch surfaces a popup but the file is still saved
- Device-side gating: the Teensy enters STANDBY automatically whenever USB is connected (host port open or charger active). In STANDBY, recording is stopped, the file is fully closed, and MTB commands work. There is no manual TRANSFER-mode button anymore

## Input format — Teensy MTB DAQ CSV (SW_VERSION 56), fixed 240 Hz
The analyzer targets **Teensy_MTB_DAQ** logs only (the old Open_Log_Artemis format is no longer supported).

**Self-describing header block (firmware `writeHeader`).** New logs begin with a `#`-prefixed block before the column header:
```
#MTB_DAQ,1                       <- magic + format version
#CFG,device_name,Transition Smuggler
#CFG,fork_v_extended,4.500       <- fork/shock/speed cal + device settings (keys match CONFIG.CSV)
#CFG,fork_v_compressed,0.500
#CFG,fork_travel_mm,225.0
#CFG,shock_v_extended,4.310
#CFG,shock_v_compressed,0.561
#CFG,shock_travel_mm,75.0
#COLUMNS                         <- marker: the NEXT line is the column header
time,drops,...,event
```
`file_manager._parse_log_header(path)` reads this block into `self._log_config` (values → float where parseable) on load — the first loaded file that has one wins. The data read still uses `comment="#"`, which skips the whole block (and the trailing `# ring_hwm` footer) and picks up the `time,...` line as the header, so old logs without the block load unchanged. **The fork/shock `#CFG` cal values auto-update the calibration table on load** — see the Raw→calibrated mapping section. Column header:
```
time, drops, spd1_hz, spd2_hz, spd3_hz,
accel_x, accel_y, accel_z,            # m/s²  (raw IMU body frame)
gyro_x, gyro_y, gyro_z,              # rad/s (raw IMU body frame)
quat_x, quat_y, quat_z, imu_temp_c,  # SFLP game-rotation-vector vector part (body frame)
analog1_v, analog2_v,                # sensor-side volts (0–5 V): analog1=front fork, analog2=rear shock
gps_lat, gps_lon, gps_alt, gps_spd, gps_sats,
batt_soc, power_w, cadence_rpm, event
```
- **`time` is `HH:mm:ss.sss` with no date** — the date comes from the RTC-stamped **filename** (`YYYYMMDD_HHMMSS.csv`). `file_manager._build_datetime_index` combines them and handles a within-file midnight rollover.
- Lower-rate channels are **NaN-filled at 240 Hz** (GPS 10 Hz, BLE ~1–4 Hz, batt 1 Hz, speeds only on a trigger capture). Sparse channels plot as dots via the existing >50 %-NaN rule.
- The logger appends a trailing `# ring_hwm=… ` summary line — the loader passes `comment="#"` to drop it.
- **The CSVs in `~/Documents/MTB_DAQ/Archived_Data/` are OLD-system data — do not use them to validate.**

## Signal Calibration Tab (calibration.py — CalibrationMixin) — explicit apply, no auto-update
- **RULE: nothing on this tab recomputes or redraws automatically as you edit.** Typing in the form fields (Raw/Value min-max, Bias, New Calibrated Signal Name) only sits in the widgets — it does **not** write to `saved_calibrations`, does **not** recompute `cal_result_df`, and does **not** refresh any tab (including this tab's own preview plots). This was a deliberate change (2026-07) from the old per-keystroke `_sync_form_to_table` binding, which fired the full `_apply_all_calibrations()` cascade (recompute + redraw all 8 analysis tabs) on every keystroke.
- **`Apply Updates` button** (top of the tab, `apply_calibration_updates`) is the only way edits take effect: `_commit_form_to_table()` writes the form into the currently-selected signal's `saved_calibrations` row (and refreshes its Calibrated_Min/Max via `_recompute_calibrated_range`), then `_apply_all_calibrations()` recomputes `cal_result_df` + refreshes every analysis tab, then `_update_cal_plots(autofill=False)` refreshes this tab's own raw/calibrated/histogram preview.
- Selecting a row in the saved-calibrations treeview (`on_cal_tree_select`) or picking a raw signal in the "Signal to calibrate" combo still update live — those are pure navigation/preview (loading from or browsing existing state), not edits, so they don't need Apply.
- **Automatic suspension zero-min calibration (no buttons).** Fork/shock are zeroed **automatically inside `_apply_all_calibrations`** (every load / Apply / Auto-Cal) — the old manual `Auto-Cal Fork/Shock (Zero Min)` buttons and `_auto_calibrate_zero_min` were removed. For each suspension signal the loop computes the zero-bias calibrated mm (`a·raw + b`), **masks out-of-range voltage first** (`_mask_voltage_out_of_range` — so a sensor fault / topout overshoot can never set the zero, which was the bug in the old manual version that took `min()` of the *unmasked* raw), then sets `Bias = nanmin(masked)` so the fully-extended (minimum **valid**) reading becomes exactly 0 mm. The min is over the **full ride** (`self.df`) — the stopped/walking view filters are NOT applied to this computation, so a topout captured while the bike is lifted at a stop still counts. The computed bias is written back into the `saved_calibrations` row (so the table/form show it) and is idempotent (recomputed from the zero-bias series each run). Note: because it always overrides, a **manual** Bias edit on a fork/shock row is replaced by the auto value on the next apply. **Usage tip:** lift the bike once before a ride so a true full-extension sample is captured.

## Performance (2026-07) — the calibration cascade + file load are the app's slow paths
`_apply_all_calibrations()` (recompute `cal_result_df` + redraw all 8 analysis tabs) runs on every file load, "Apply Updates", and Auto-Cal click — it's the single most expensive operation in the app, so it's had two rounds of attention:

- **Speed fixes** (measured on a synthetic 30-min/240Hz/432k-row ride):
  - **⚠ Dynamic Sag replaced by `Filt_` channels (2026-07-20):** the old `Front_/Rear_Dynamic_Sag_Perc` (single forward one-pole, mean-centred) were deleted and replaced by a general **zero-phase `Filt_` filtering** primitive — see "Filtered (Filt_) trend channels" below. The `_time_varying_lowpass` helpers are **called again** (twice per signal, forward + backward, by `_filt`).
  - **`_time_varying_lowpass` (calibration.py)** replaces the old per-row Python loop for the Dynamic Sag filter (front + rear) with a numerically-exact **blocked vectorized** computation (`_time_varying_lowpass_loop` kept as the literal old code, used only as a fallback). The naive recursion `y[i]=a[i]·x[i]+(1-a[i])·y[i-1]` has a closed form via a cumulative product, but a single global cumprod underflows to 0 over long rides — so it's computed in ~4096-row blocks, carrying the true running value forward as each block's initial condition (safe because the filter's ~0.3 Hz cutoff means old samples decay to ~0 within a few thousand rows anyway). Validated against the loop to ~1e-13 abs error across normal data, duplicate timestamps, and multi-file gap boundaries. **Falls back to the exact loop if the signal contains any NaN.** ~150x faster (0.71s → ~0.005s per signal on the 432k-row benchmark) — was ~70% of total cascade time. **Note (2026-07-11):** the fork/shock out-of-range voltage masking (see "Suspension out-of-range voltage masking" below) now *can* introduce NaN into `Fork_Pos_mm`/`Shock_Pos_mm` and thus into `Front_/Rear_Wheel_Pos_Perc`, so whichever of front/rear had a masked sample drops to the slower loop for its Dynamic Sag pass — measured ~+1.6s on the 81-min ride when only the front had faults. This is no longer a "defensive-only" path.
  - **`legend.loc` global default (MTB_DataLog_Analyze.py)** set to `"upper right"` instead of matplotlib's default `"best"`. `loc="best"` searches candidate positions against every plotted artist to avoid overlapping data — with a few hundred thousand points per axes that search alone measured **~0.7s per legend call**. A fixed corner is ~6.6x faster and applies to every `legend()` call in the app with no explicit `loc=`. **Call sites whose upper-right corner is already occupied by a fixed annotation override to `"upper left"`**: `plots.py` (Select Data histogram's stats box) and `free_histogram.py` (same). (`susp_speed.py`'s old scatter with quadrant labels was removed 2026-07-13; its remaining comp/rebound legends use the default corner.)
  - **`FileManagerMixin._fast_time_to_timedelta` (file_manager.py)** replaces `pd.to_timedelta(raw["time"].astype(str))` for the fixed `HH:MM:SS.sss` format with a vectorized byte-level parse (view the string column as fixed-width bytes, subtract `'0'` to get digit values, combine with pure integer arithmetic — no float rounding, so bit-exact with `pd.to_timedelta` when taken). ~6.5–12x faster (0.35s → ~0.03–0.06s on the benchmark). **Validates the exact 12-char `DD:DD:DD.DDD` shape first (all-vectorized) and falls back to the original `pd.to_timedelta` call, unchanged, if anything doesn't match** — e.g. a row truncated by a power-loss mid-write — so malformed-data behavior (NaT, whatever quirks `pd.to_timedelta` has) is preserved exactly, only well-formed data takes the fast path.
  - Net effect on the benchmark ride: file load (read + preview + header-triggered cascade) **7.1s → 5.2s**; a subsequent Apply Updates / Import **4.65s → 3.1s**. The remaining time is legitimate matplotlib rendering across 8 tabs and CSV parsing — further large wins would need either down-sampled/decimated plotting or deferring redraws for tabs the user isn't currently viewing (not implemented — a bigger architectural change, not attempted here).
- **Progress dialog (`widgets.ProgressDialog`)**: a modal "please wait" window (determinate progress bar + status label naming the current step + live elapsed/estimated-remaining time) shown during all three of the above operations (`file_manager.on_file_select`/`_on_file_select_settled`, `calibration.apply_calibration_updates`/auto-cal). Now debounced 150 ms (`self.after` cancel/reschedule, same pattern as `gps._gps_on_resize`) so only the settled selection actually loads.

### Frequency tab is opt-in (2026-07) — was a 47s hang on real ride data
Root-caused against a real ride (`20260703_200146_Smuggler.csv`, ~116k rows) that hung for ~47s on every load/Apply — the progress dialog's last step before the stall was "Redrawing Frequency tab…". Two compounding issues, both fixed:
- **`_update_frequency_plot` no longer runs automatically.** It's opt-in via a **"Compute Frequency Analysis" button** at the top of the Frequency tab (`frequency._compute_frequency_plot`, wired to the button). Most sessions never open this tab.
- **Root cause of the 47s, fixed regardless of the button (so a click doesn't just move the hang):** `series.resample(f"{median_dt_ms}ms")` bins across the **full calendar span of the index**, regardless of how sparse the data actually is. This ride had two suspiciously round gaps — exactly 4.00h and 20.00h (device left idle/paused mid-recording, or a firmware RTC artifact — worth separately investigating on the firmware side, unrelated to this fix) — turning a 116k-row series into a **~22M-row resampled one** per signal (×3 signals ≈ the observed ~47s). **Update 2026-07-11:** the *current* copy of `20260703_200146_Smuggler.csv` (same 116,101 rows) now loads with a max gap of **0.094s — no large gaps at all**, so the file was evidently re-offloaded/replaced since, or those gaps were a since-fixed datetime-parse artifact rather than logged data. On the same ride: 47s → **0.06s**.
- **Check for recurrence:** this `resample()`-across-full-span trap could bite any other code that calls `.resample()` on a `cal_result_df` column without first checking for/segmenting around large gaps. `frequency.py` is currently the **only** call site (`grep -rn "\.resample(" *.py`) — if a new one is added, apply the same gap-segmentation pattern.

## Raw → calibrated name mapping (the calibration table is the mapping layer)
Downstream tabs key off the *calibrated* names, set by `__UserFiles/Calibration_Config/Default_Calibration_Config.csv`:
- `analog1_v → Fork_Pos_mm` / `analog2_v → Shock_Pos_mm` — volts→mm. **Auto-calibrated from the CSV `#CFG` header on load** (`calibration._apply_log_config_to_calibrations`): each row is set from the per-device config so that compressed volts → sensor travel (mm) and extended volts → 0 mm — i.e. `Raw_Sig_Min=<fork/shock>_v_compressed → Value_at_Min=<…>_travel_mm`, `Raw_Sig_Max=<…>_v_extended → Value_at_Max=0`. Falls back to the `Default_Calibration_Config.csv` seed values (Honeywell datasheet sensitivities: fork −17.78 mV/mm, shock −50 mV/mm) for older logs with no header. User can still override per ride.
  - **Suspension out-of-range voltage masking (2026-07-11, `calibration._mask_voltage_out_of_range`).** The fork/shock voltage is physically bounded by the sensor's rated endpoints, so during the raw→calibrated loop in `_apply_all_calibrations`, any sample of `analog1_v`/`analog2_v` (identified via `_HEADER_SUSP_CAL`) whose voltage falls **outside `[min, max]` of that row's `Raw_Sig_Min`/`Raw_Sig_Max`** has its calibrated `Fork_Pos_mm`/`Shock_Pos_mm` set to **NaN** — these are sensor-fault / topout-overshoot readings (e.g. the July-10 Smuggler ride hit 4.865 V vs a 4.5 V rated extended endpoint → an impossible −20.5 mm before masking). Around every masked run, a **±`_VOLTAGE_MASK_BUFFER_S` (20 ms) guard band** of extra NaN is added (the mask is dilated by a centered rolling-max over `2·buf+1` samples, `buf = round(0.020/period)` derived from the data rate — never hardcoded), because a downstream filter whose window straddles the bad sample (Savitzky-Golay velocity, dynamic-sag low-pass) would otherwise smear the fault into good neighbours. All indexing is positional so duplicate multi-file timestamps can't cause index-alignment blow-ups. Masking is scoped to the suspension channels only — other calibrated signals (accel/gyro/etc.) use their `Raw_Sig_Min/Max` purely as a scale line, not a physical bound, and are not masked. On the July-10 ride: 21 raw over-voltage samples in 7 runs → 87 NaN after buffering (0.01%).
- `accel_x/y/z → aX_g/aY_g/aZ_g` (×1/9.80665), then rotated → `aFwd_g/aVert_g/aLat_g`.
- `gyro_x/y/z → gX_DPS/gY_DPS/gZ_DPS` (×180/π), then rotated → `gRoll_DPS/gPitch_DPS/gYaw_DPS`.
- `spd1→Front_Horz_Wheel_Spd_mph`, `spd2→Rear_Horz_Wheel_Spd_mph`, `spd3→Crank_Spd_RPM` (see below).
- `imu_temp_c→Board_Temp_C`, `batt_soc→Batt_SoC`, `power_w→BLE_Power_W`, `cadence_rpm→BLE_Cadence_RPM`, `gps_lat/lon/alt/sats`, `quat_*` pass through.
- **`gps_spd` is always converted m/s→mph and renamed `gps_spd_mph`** (`_apply_all_calibrations`, ×2.23694, right after `cal_result_df` is built — independent of the calibration config). The firmware logs `gps_spd` in m/s (`gps.speed_mps`).
- There is **no magnetometer** on the LSM6DSV16X — all `m*_uT` features are removed.
- **Spring-force / load-distribution channels** (`Fork_/Shock_Load_N`, `Front_/Rear_Vert_Load_N`, `Front_Load_Bias_Perc`, `Pedal_Only_Ref_Bias_Perc`; unit tokens `N`, `Perc`) come from **`model_ip.py`** — the proprietary force model. It is **committed** (this repo is PRIVATE). `_apply_all_calibrations` calls it through an import guard (`_HAS_MODEL_IP` — retained so the app still runs if the file is ever pulled out), passing the Bike-Params spring-rate / preload / head-angle / chainstay / front-center / BB-height fields + the motion-ratio table. Model is **spring-only** (damper deliberately ignored), linear `F = k·(shaft displacement + preload)`:
  - `apply_model_IP()` → `Fork_/Shock_Load_N` = shaft spring forces; `Front_Vert_Load_N` = fork force · sin(HTA) (fork inclined at the head angle); `Rear_Vert_Load_N` = shock force ÷ **local motion ratio** `d(wheel)/d(shock)` (MR-table gradient interpolated per sample — virtual work); `Front_Load_Bias_Perc` = 100·Fv/(Fv+Rv), NaN when total < 1 N (unloaded / airborne). `Front_Load_Bias_Perc` also gets a `Filt_` twin via `FILT_SIGNALS`.
  - `front_weight_bias_IP()` → `Pedal_Only_Ref_Bias_Perc` = a QUASI-STATIC front weight-distribution **reference** for the rider standing on the pedals (weight applied ONLY at the BB): `front% = 100·chainstay/wheelbase − (BB_height/wheelbase)·tan(Filt_Pitch_deg)·100`. Bike-only static free body (external forces at just the two tire contact patches + the BB); at zero pitch it reduces to the constant `chainstay/wheelbase` (= `static_pedal_front_bias_IP()`), and the BB-height·tan(pitch) term shifts weight rearward climbing / forward descending using the FILTERED pitch. Computed **after** `_apply_filt_channels` (needs `Filt_Pitch_deg`). Governing assumption is bike-only static: no rider-CoG height, accel, braking, or pedaling-torque terms (see the docstrings).
  - Full formulas + derivations live in `model_ip.py`'s docstrings. **This is flagged POTENTIAL IP:** the repo is private so the file is committed, but it's kept isolated for easy separation if the repo ever goes public — the `_ip.py` filename + `_IP` function suffix are the grep markers, and the `_HAS_MODEL_IP` import guard means removing the file just drops these channels (the rest of the app is unaffected). To publish: pull `model_ip.py` out and re-add `*_ip.py` to `.gitignore`.
- **`Gear_Selected`** — nearest cassette gear from the apparent sprocket teeth (`chainring_teeth · crank_rpm / wheel_rpm`, nearest to the Bike-Params cassette). **Gated on SUSTAINED pedaling:** valid only where `Crank_Spd_RPM > GEAR_MIN_CRANK_RPM` (30) held continuously for ≥ `GEAR_SUSTAIN_S` (3 s) — everywhere else **NaN** (coasting/stopped: the chain isn't driving, so the ratio is meaningless). Within a sustained run the gear is **latched** to the dominant value over the sustain window (centered rolling median), so it holds steady and only changes once a new gear is held long enough — no per-sample flicker. Constants in `constants.py`; validated on 20260710_144915 (gear valid 52% of the ride, NaN 100% where crank ≤ 30).

## Filtered (Filt_) trend channels (calibration.py `_filt` / `_apply_filt_channels`)
A general **zero-phase (forward-backward) low-pass** that strips normal bumps and leaves the slow ride-height / attitude trend, auto-generated as `Filt_<name>` twins.
- **`_filt(series)`** runs the dt-aware one-pole `_time_varying_lowpass` **forward, then again over the reversed signal, then reverses back** — the per-pass phase lag cancels, so the output is **zero-phase (no lag vs the events)**. Verified: **0.0 ms lag at every frequency**.
- **Cutoff:** two passes square the magnitude response, so each pass is designed at `FILT_PER_PASS_HZ` (**0.466 Hz** ≈ `FILT_EFFECTIVE_HZ 0.3 / 0.644`) to land the **effective −3 dB at ~0.3 Hz** (measured gain 0.704 at 0.30 Hz). Both constants in `constants.py`.
- **Robustness:** inherits the one-pole's per-sample-dt design → cutoff stays honest under irregular timing and the filter **self-resets across multi-file gaps** (big dt → coefficient→1 → follows signal); **NaN-robust** (drops to the exact loop fallback). Reverse pass reverses the dt array **and rolls it by one** so gaps align for the backward traversal.
- **`_apply_filt_channels()`** loops `FILT_SIGNALS` (constants.py) and writes `Filt_<name>` for each present column; called right after the IMU-attitude block so every source exists. Default `FILT_SIGNALS` (user-selected 2026-07-20): `Front_Wheel_Pos_Perc`, `Rear_Wheel_Pos_Perc`, `Front_Load_Bias_Perc`, `Pitch_deg`, `Roll_deg`, `aFwd_g`, `aVert_g`, `aLat_g`. To add/remove a default twin, edit that list — no other wiring. Fast (~0.005 s/signal/pass, vectorized). Replaces the old Dynamic Sag block (dynamic sag now reads off `Filt_Front_/Rear_Wheel_Pos_Perc`).

## Speed from frequency channels (calibration.py `_derive_speed`)
- `spd1/2/3_hz` are already frequency (FreqMeasureMulti), sparse/NaN-filled.
- **Measured stream structure (ride 20260703_200146, 2026-07-05)** — supersedes the old "raw Hz alternates high/low on all channels" note: the **crank** genuinely alternates ~2.5–2.7x (its 5-pair target geometry is real in the data); the **wheels** vary only mildly (0.7–1.4x consecutive — no visible pairing; effectively 12 roughly-even targets/rev). This is why despiking runs in the **pair-mean domain**, never on the raw stream — a raw-domain median would flatten the crank's genuine alternation (`median(L,H,L)=L`) and bias cadence low.
- **Chatter despike (2026-07-05):** all three prox sensors occasionally emit an extra falling edge inside a target's passage (re-trigger chatter, ~1 per 8 wheel revs), splitting one normal gap in two — an isolated raw Hz spike of ~4.5–5.5x (wheels) / ~3–5x (crank); verified physically real (spike period + next period == one normal gap). Two stages on the pair-mean, both required: (1) drop pair-means > 1.8x their local rolling median-31 (handles double-chatter runs a small median can't clip), then (2) rolling median-5 polish for the ~1.25–1.45x remainder-gap wiggle. The two stages run **twice** (pair-average once, then stages 1+2 applied a second time to their own output) — capped at one extra pass. Validated: derived-speed samples >2x local median 200/194/185 → **0/0/0** (front/rear/crank), medians preserved within 1%. Firmware ≥ v79 also rejects wheel chatter at capture time (`speed.cpp`, `configSpdRetrigRatioFront/Rear()`, default 2.5x — a `CONFIG.CSV` setting since v80/v81); ≥ v81 also lightly filters the crank (`configSpdRetrigRatioCrank()`, default 6x — deliberately loose since the crank's genuine ~2.9x pair alternation is too close to its own chatter range for a tight ratio, so it only catches the most extreme outliers). **The analyzer despike remains the primary cleanup regardless of firmware version** — it cleans pre-v79/v81 logs and catches the crank chatter (~3–5x) the loose 6x firmware ratio lets through.
- **Stage-1 window widened 15→31 (2026-07-05):** even with an improved sensor bracket/mount, a residual crank spike was still visible. Root cause: sustained bursts of 3+ consecutive spurious raw captures (~9 events out of 358 chatter events on the reference ride) could partly contaminate stage 1's local-median reference, letting some burst samples slip under the 1.8x cutoff. Widening the reference window to 31 samples (~2.1s of pedaling at this ride's ~67ms/pair-mean spacing) dilutes that contamination — validated: residual "hot" (>1.5x a 101-sample reference) samples dropped 32→19, and the two worst multi-sample plateau runs (length 6 and 9) that survived at window-15 are eliminated entirely. Front/rear wheel medians and drop counts are effectively unchanged by the wider window (their chatter is isolated single-edge, not burst). **Not widened further** — at ~67ms/pair-mean, 31 samples already spans ~2.1s; a much wider window would make the filter slow to track a genuine fast cadence change (e.g. a sprint start) and risk rejecting real data as chatter.
- **Known residual limitation (2026-07-05, crank only):** the mildest bursts (~1.5–1.7x true cadence) survive at **any** window width, because their own elevation ratio sits genuinely below the 1.8x cutoff — that isn't reference contamination, it's the threshold intentionally staying clear of genuine cadence variation. Verified directly: at window-15, -31, -51, and -101 the same example burst sample (29.1 Hz vs. ~18.7 Hz true) computes to the same ~1.5–1.6x ratio regardless of window size. Reaching those would require lowering the 1.8x ratio itself, at the cost of false-positiving on real speed changes — not pursued.
- Recipe: average 2 consecutive Hz readings (pair-mean) → despike as above → ÷ triggers-per-rev (wheel 12, crank 10) → rev/s; `RPM = rev/s·60`, `mph = rev/s·circ_in·3600/63360`. Hold each sparse value via `.reindex(df.index).ffill(limit=…)` where the limit is derived from the data rate, NOT hardcoded. **✅ VALIDATED (2026-07-05): triggers/rev cross-checked against GPS ground speed — implied ~12.6 targets/rev on the rear wheel, so ÷12 is correct; crank ÷10 yields a plausible ~107 RPM pedaling median on the same ride.**
- Triggers-per-rev come from the bike-params "Triggers/Rev" fields (defaults 12/12/10).
- Series assignment uses `.reindex(self.df.index)` — DO NOT use `series.loc[list] = vals` (fails on duplicate timestamps from multi-file concat).

## IMU rotation & quaternion attitude (calibration.py)
- The IMU is installed: **+X back & θ down, +Y down & θ forward, +Z right** (θ = `pitch_offset_var`, default 30°). A single fixed body→vehicle rotation maps raw body-frame accel/gyro into ISO 8855 (X fwd, Y left, Z up): `fwd=-cosθ·x+sinθ·y`, `lat=-z`, `up=-sinθ·x-cosθ·y`. Rest check: chip reads +g up → `aVert_g≈+1g`.
- Attitude `Pitch_deg/Roll_deg/Yaw_deg` comes from the **SFLP fusion quaternion** (qw reconstructed via `sqrt(1−x²−y²−z²)`), composed with the mount rotation and a rest-pose offset, via `scipy …Rotation.as_euler("ZYX")`. Quaternion NaN → attitude NaN (no fabricated values). The old complementary filter is gone. **✅ Signs validated against GPS ground truth (2026-07-13, ride 20260710_144915):** `+Pitch = nose-up` — strict ISO ZYX gives nose-DOWN-positive, so the code **negates pitch** (both `Pitch_deg` and the `gPitch_DPS` rate) to the intuitive nose-up convention; after the negation `corr(Pitch, GPS climb-rate) = +0.39` over sustained grades (and `corr(dPitch/dt, gPitch_DPS)=+0.85`, angle/rate consistent). `+Roll = lean right` and `+Yaw-rate = left turn` are ISO and were **left unchanged** — validated correct: left turn → `gYaw +6.7 dps` & `Roll −4.3°` (lean left), right turn → `−6.8 dps` & `+1.8°`; `corr(gYaw, GPS turn)=+0.54`, `corr(Roll, GPS turn)=−0.30`. Angles are **relative to the first valid sample's pose** (`_R_ref`) — a non-level bike at record-start biases the pitch/roll zero; **Yaw has no absolute reference** (no magnetometer). ⚠ History: an earlier (2026-07-11) "validation" via `corr(aFwd_LP, −sin Pitch)` was **circular** (both signals share the accel forward sign) and wrongly concluded pitch was fine; the GPS-anchored tests above supersede it.

## Suspension/wheel velocity (calibration.py `_savgol_velocity`)
Per the firmware design (`doc/suspension_daq_sampling_rate.pdf`), velocity is derived OFFLINE from logged position as a Savitzky-Golay first derivative: `savgol_filter(pos, window_length=7, polyorder=6, deriv=1, delta=sample_period)`. Outputs `Front_Vert_Wheel_Spd_mmps` / `Rear_Vert_Wheel_Spd_mmps` (mm/s).

## Signal Naming Convention
Calibrated/derived signal names are CamelCase words plus a unit suffix using **standard unit capitalization**: `W` (watt), `g` (gravity), `m`/`mm` (metre/millimetre), `deg` (degree), `C` (Celsius), and the capitalized tokens `SoC`, `DPS`, `RPM`. Compound rate tokens: `mph`, `mps` (m/s), `mmps` (mm/s), `Perc` (percent). Examples: `BLE_Power_W`, `BLE_Cadence_RPM`, `Crank_Spd_RPM`, `gPitch_DPS`, `Batt_SoC`, `Fork_Pos_mm`, `Front_Vert_Wheel_Spd_mmps`, `Board_Temp_C`, `Pitch_deg`, `Fork_Pos_Perc`. Apply consistently to every new calibrated name. **Prefix `Filt_`** marks a zero-phase low-pass trend twin of the same-named signal (e.g. `Filt_Pitch_deg`) — see "Filtered (Filt_) trend channels".

## No Hardcoded Sample Rates
Never hardcode the log rate (it is nominally 240 Hz but must not be assumed). Always derive the period/rate from the loaded data's time index via `widgets.sample_period_s()` / `sample_rate_hz()` (median of `index.diff()`), and use it for filter `delta`, dt windows, and ffill limits.

## Code Style
- Partition logic heavily into small, focused sub-functions — avoid large monolithic functions
- Maximize reuse: if similar logic appears more than once, extract it into a shared helper
- Never use a companion "fresh" or "valid" boolean column alongside a data value — instead return NaN directly in the data field when the value is absent, stale, or invalid
- Always read the manufacturer datasheet for any interfaced hardware before writing configuration code — do not assume defaults or rely on library behaviour alone. Present all relevant configuration options to the user and confirm choices before implementing

## Key Constraints & Gotchas
- Use Homebrew Python (`.venv/`) — system Python on macOS is incompatible with Tkinter
- ttk theme must be `clam`, not `aqua` — Aqua theme ignores custom button background colours
- Multi-file load uses `pd.concat` + `sort_index`; duplicate timestamps are expected — do not drop them
- `series.loc[list] = vals` fails with duplicate DatetimeIndex — always use `.reindex()` pattern instead
- `insert_gap_nans` must be applied before plotting to prevent line segments bridging data gaps
- Tk `after(0, …)` from a non-main thread acquires Tk's lock — calling it from a worker every chunk of a serial download will starve the worker (sustained throughput collapses from MB/s to KB/s). Throttle UI updates from worker threads to ~10 Hz
